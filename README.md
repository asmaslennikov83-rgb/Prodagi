# WB Procurement Bot — расчёт закупок Wildberries

## Автоматический учёт дней наличия

CSV WB читается с поддержкой экранированных двойных кавычек внутри названий
и артикулов. Автоопределяется только разделитель, а не правила экранирования:
неверное автоопределение раньше сдвигало колонки у товаров с кавычками и запятыми.
Число полей записи проверяется до сопоставления товаров.
Отдельно различаются отсутствие товара в выгрузке WB, отсутствие некоторых
дат/значений и некорректные числа. Прочерк WB считается отсутствующим значением,
а не нулевым остатком. Для неполной истории показывается число известных дней.
Эти предупреждения сохраняются: по отсутствующим данным нельзя восстановить
фактические дни наличия задним числом.
Отсутствие строк, дат и значений показывается на листе «Предупреждения».
Ошибки формата чисел и ошибки API остаются на листе «Ошибки».
Сообщение Telegram отдельно показывает обе категории и общее количество
товаров/размеров, для которых применены календарные дни.

Ошибки значений в отдельной строке CSV больше не отключают историю всего
кабинета. Календарные дни используются только для затронутого товара/размера;
остальные товары продолжают использовать корректную историю. В примечании
и на листе «Ошибки» указаны CSV, строка, дата, поле и исходное значение.
Пустое, отрицательное или некорректное значение не заменяется нулём.
Пробелы-разделители, включая неразрывные и узкие неразрывные, допускаются
в числах. Если в истории ошибочен комплект, календарные дни используются
для скорости этого комплекта; прямые заказы компонента и другие комплекты
по-прежнему рассчитываются по собственной истории.

При обычном расчёте закупки и ручной проверке бот сам получает историю остатков
за выбранный период по каждому выбранному кабинету. Отдельная команда не нужна.
История кэшируется в `data/stock_history` на 2 часа отдельно по токену и датам.
Одновременные запросы одного периода внутри процесса используют одну загрузку.
Для работы токены должны иметь доступ к категории «Аналитика».

Для каждого товара/размера в каждом кабинете считаются дни с положительным
остатком на конец дня плюс дни с неотменёнными заказами.
В режиме «Только FBS» запрашивается история только складов продавца
(`stockType=mp`), и к дням наличия добавляются только дни заказов FBS.
Наличие товара на FBO и заказы FBO не увеличивают число дней наличия FBS.
В остальных режимах сохраняется история FBO+FBS и дни заказов обоих типов.
Кэш истории FBS хранится отдельно от общей истории, поэтому переключение
режима не использует старые данные FBO+FBS вместо FBS. Это действует также
для готовых комплектов и ручной проверки. На листе «Наличие» указан источник.
Числитель скорости остаётся прежним: заказы FBO+FBS; выбор «Только FBS»
меняет дни наличия и вычитаемые остатки, но не отфильтровывает заказы FBO.
Скорость прямых заказов = прямые заказы / дни наличия этого товара.
Скорость каждого комплекта считается по его собственным дням наличия,
затем умножается на кратность компонента и добавляется к скорости компонента.
При 14 заказах за один подтверждённый день целевой запас на 14 дней — 196 шт.
до коэффициента и вычета остатков. Это оценка по дневным снимкам, не учёт часов.

Excel содержит дни наличия и средний расход по кабинетам. Лист «Наличие»
показывает основание расчёта по каждому исходному товару, включая комплекты.
Если история недоступна, её формат не распознан или нет всех дней выбранного
периода по конкретному размеру, используется прежний расчёт по календарным дням.
Причина указывается в примечании, на листе «Ошибки» и в ручном ответе Telegram.
Отсутствующая строка не считается нулевым остатком. При 0 заказов закупка равна 0.
Лимит истории — последние 3 календарных месяца; для более старых дат также
выводится предупреждение о расчёте по календарным дням.

## Диагностическая выгрузка исходной истории

Отправьте боту `/stock_history 14` (или другой период от 1 до 90 дней).
Бот создаст отчёт `STOCK_HISTORY_DAILY_CSV` по каждому кабинету, дождётся статуса
SUCCESS и отправит исходные ZIP с CSV в Telegram. Используются токены WB из
существующего `.env`, категория «Аналитика». Запрашиваются оба типа склада.
Ошибки одного кабинета не препятствуют попытке получить второй.
За один запуск создаётся до двух отчётов, по одному на кабинет. Не повторяйте
команду во время формирования: WB ограничивает создание 20 отчётами в сутки
на кабинет. Каждый кабинет ожидается до 5 минут плюс время сетевых запросов.
ZIP ограничен размером 50 МБ; более крупный отчёт запросите за меньший период.
Даты считаются по Москве. WB разрешает окно последних трёх календарных месяцев;
даже период 90 дней у границы окна иногда недоступен.

Команда оставлена для диагностики. Обычный расчёт загружает и учитывает историю
автоматически, исходный ZIP отдельно пользователю не отправляется.

Документация: https://dev.wildberries.ru/docs/openapi/analytics#tag/Analitika-prodavca-CSV

## Потребность по кабинетам

Целевой запас округляется вверх отдельно по каждому кабинету по его заказам,
включая расход компонентов через комплекты. Потребность кабинета равна
max(0, целевой запас − FBO этого кабинета) в режимах FBO/FBO+FBS.
Избыток FBO другого кабинета не закрывает эту потребность.
В режиме FBS потребность кабинета равна его целевому запасу.
Общая потребность — сумма потребностей кабинетов. Общий FBS вычитается один раз
из этой суммы в режимах FBS/FBO+FBS; в режиме FBO не вычитается.

Excel показывает FBO, целевой запас и потребность каждого выбранного кабинета,
общую потребность до вычета FBS и итог «К закупке» сразу после наименования.
При выборе одного кабинета рассчитывается только его потребность.
Остатки готовых комплектов FBO также относятся к своему кабинету.

В полном отчёте общий FBS берётся из загруженного файла склада. В ручной
проверке используются остатки WB API: для одного товара берётся максимум
остатков двух кабинетов вместо суммы. Для каждого готового комплекта действует
то же правило. Это оценка общего склада по размещённым остаткам WB; если
кабинеты показывают разные части физического склада, она не равна фактическому
остатку. Физический остаток из файла используется только в полном отчёте.

«На сколько хватит дней» остаётся общим показателем: суммарный учтённый остаток
делится на общий средний расход. Он не отражает нехватку отдельного кабинета;
для неё используются отдельные колонки потребности.

После завершения ручной проверки бот автоматически отправляет главное меню.
Меню появляется также при ошибке, отсутствии шаблона или ненайденном ШК.

## Исключение ошибочных штрихкодов

`EXCLUDED_BARCODES=4600987014272` задаёт исключённые ШК через запятую в `.env`.
Если настройка отсутствует, по умолчанию исключается `4600987014272`.
Пустое значение отключает исключения. После изменения настройки перезапустите бота.

Исключённые ШК удаляются из списка баркодов карточек до сопоставления заказов,
комплектов и остатков и не связывают товары между кабинетами. Карточки, их заказы
по остальным ШК и остатки по идентификаторам WB сохраняются. Если заказ всё же
приходит с исключённым ШК, остаётся сопоставление по идентификатору WB; без него
заказ попадёт в число несопоставленных. Ручной ввод исключённого ШК предлагает
использовать другой ШК товара.

Для А5 используется `4600987012193`, для А6 — `4600987012223` и `4600987014289`.
Исходные файлы остатков и комплектов не изменяются; исключённый ШК в них не
переназначается автоматически другому товару.

Telegram-бот рассчитывает закупку на основе заказов FBO + FBS, физического остатка на вашем складе и готовых комплектов/наборов.

## Как работает

1. Пользователь выбирает кабинет: кабинет 1, кабинет 2 или оба.
2. Выбирает период анализа продаж: 7 / 14 / 30 / 60 / 90 дней или свои даты. Быстрые периоды не включают сегодняшний день.
3. Выбирает целевой товарный запас: 1 / 2 / 3 / 4 недели (7 / 14 / 21 / 28 дней).
4. Выбирает коэффициент: 0,5 / 0,75 / 1 / 1,25 / 1,5.
5. Загружает файл остатков `.xls` или `.xlsx` с колонками `Код` и `Доступно`.
6. Загружает шаблон комплектов `.xls` или `.xlsx`.
7. Бот получает заказы WB, учитывает FBO и FBS, раскладывает проданные комплекты на компоненты, раскладывает остатки готовых комплектов в физический остаток компонентов и формирует Excel.

## Формула

- `Общий расход = FBO + FBS + расход компонентов через проданные комплекты`
- `Среднее в день = прямые заказы / дни наличия товара + сумма(заказы каждого комплекта / дни наличия комплекта × кратность компонента)`
- `Необходимо иметь = округление вверх(Среднее в день × целевой запас в днях × коэффициент)`
- `Физический остаток = отдельный остаток компонента + компоненты внутри готовых комплектов`
- `К закупке = max(0, сумма потребностей кабинетов после вычета своего FBO − общий FBS)`

Остатки вычитаются в выбранном режиме FBO/FBS/FBO+FBS. FBO уменьшает потребность
только своего кабинета; общий FBS учитывается один раз, включая готовые комплекты.

## Шаблон комплектов

Поддерживается структура:

- `Название`
- `баркод комплекта`
- `баркод1`
- `баркод2`
- `баркод3` ...

Если один и тот же баркод указан несколько раз, это означает кратность. Например `баркод1 = 460...` и `баркод2 = 460...` означает 2 единицы этого компонента в комплекте.

## Итоговый Excel

### Лист `Закупка`

Баркод(ы), Артикул продавца, Бренд, Наименование, К закупке, На сколько хватит дней, Размер, Заказы FBO, Заказы FBS, Продажи комплектами, Общий расход, Среднее/день, Запас дней, Коэффициент, Необходимо иметь, Остаток FBO, Остаток FBS, Остаток учтён, Примечание.

### Лист `Комплекты`

Показывает заказы каждого комплекта, его остаток, состав и влияние на расход/остаток компонентов.

### Лист `Ошибки`

Неизвестные баркоды комплектов, компонентов, лишние баркоды из файла остатков и другие проблемы сопоставления. Ошибка в одной строке не останавливает весь отчёт.

## Доступ пользователей

В `.env`:

```env
ALLOWED_TELEGRAM_IDS=123456789,987654321
```

Пустой список запрещён — бот не запускается, чтобы случайно не открыть доступ всем.

## Настройка `.env`

Скопируйте `.env.example` в `.env` и заполните:

```env
TELEGRAM_BOT_TOKEN=...
WB_API_KEY_1=...
WB_API_KEY_2=...
CABINET_1_NAME=Кабинет 1
CABINET_2_NAME=Кабинет 2
ALLOWED_TELEGRAM_IDS=123456789
```

## Важно

- Для старого формата `.xls` используется `xlrd`.
- Для `.xlsx` используется `openpyxl`.
- Сам баркод комплекта не попадает в лист закупки: закупаются его физические компоненты.
- Если товар отсутствует в файле остатков, его остаток считается равным 0 и в строке появляется примечание.
- Если товар не продавался, он остаётся в отчёте с закупкой 0.


## Выбор учитываемых остатков
После выбора коэффициента бот предлагает:
- Только FBO — текущие остатки на складах Wildberries через Analytics API; файл остатков FBS не нужен.
- Только FBS — остатки из загруженного файла склада.
- FBO + FBS — сумма текущих остатков WB и остатков из загруженного файла.

В обоих источниках остатки готовых комплектов разворачиваются в физические компоненты по шаблону комплектов.

В листе «Закупка» добавлена колонка «Бренд» перед «Наименование», а также отдельные колонки остатков FBO/FBS и фактически учтённого остатка.


## Обновление отчёта

На листе «Закупка» столбец «К закупке» расположен сразу после «Наименование». Следом добавлен столбец «На сколько хватит дней» = «Остаток учтён» / «Среднее/день». При нулевой средней скорости продаж значение равно 0.


## Ручная проверка по ШК

В главном меню доступна кнопка `🔎 Ручная проверка по ШК`. Бот запрашивает один баркод, период анализа, целевой запас 1–4 недели, коэффициент и режим остатков. Проверка всегда выполняется сразу по двум кабинетам.

В сообщении Telegram выводятся продажи FBO/FBS отдельно по каждому кабинету, расход через наборы, общий расход и среднее в день, остатки FBO и FBS, выбранный для расчёта остаток, запас в днях, необходимый целевой остаток и количество к закупке.

Для ручной проверки используются последние загруженные пользователем файл остатков FBS и шаблон комплектов. Они сохраняются в каталоге `data` отдельно для каждого Telegram ID. В Docker каталог `./data` примонтирован как постоянный том, поэтому файлы сохраняются после перезапуска контейнера. Если нужный файл ещё ни разу не загружался, бот попросит сначала выполнить обычный расчёт закупки.

## Ручная проверка по ШК: остатки FBS

В режиме «Ручная проверка по ШК» файл остатков FBS не используется. Бот получает актуальные остатки напрямую из WB Marketplace API по всем складам продавца каждого из двух кабинетов (`GET /api/v3/warehouses` + `POST /api/v3/stocks/{warehouseId}`) и суммирует их. Последний загруженный шаблон комплектов по-прежнему используется для пересчёта комплектов в компоненты.


## Отдельная загрузка шаблона комплектов

На главном экране есть кнопка `📦 Загрузить шаблон комплектов`. Она позволяет сохранить или заменить шаблон комплектов без запуска полного отчёта. Шаблон сохраняется отдельно для каждого Telegram ID в каталоге `data` и используется в `🔎 Ручной проверке по ШК`.
